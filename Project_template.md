### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Администратор/установщик может подключить на объекте контроллер отопительного оборудования и датчик температуры к Системе
 
- Пользователи/клиенты могут дистанционно через веб-интерфейс включить или выключить отопление в своих домах, а также выставить необходимую температуру

- Система поддерживает регистрацию и подключение новых контроллеров отопления и датчиков температуры, хранит информацию о подключенном обородовании, направляет команды пользователя включить/выключить и выставить температуру

**Мониторинг температуры:**

- Пользователи/клиенты могут дистанционно просматривать информацию о текущей температуре через веб-интерфейс

- Система получает данные о температуре и направляет данные пользователю по запросу через веб-интерфейс

Проект организован в соответствии со стандартной структурой Maven/Gradle проекта:
Основной класс приложения аннотирован @SpringBootApplication.
Пакеты:
- controller - контроллеры для обработки HTTP-запросов.
- service - сервисы для бизнес-логики.
- repository - репозитории для доступа к базе данных.
- entity - сущности JPA.
- dto - объекты передачи данных (DTO).

- Язык программирования: Java 17
- Фрэймворк: Spring
- Сборка: Maven >=3.8.1 && <4.0.0
- spring-boot-starter-web - для создания веб-приложений.
- spring-boot-starter-data-jpa - для работы с JPA и базой данных.
- postgresql - драйвер для работы с PostgreSQL.
- springfox-boot-starter - для интеграции Swagger.
- lombok - для упрощения написания кода.
- spring-boot-starter-test, spring-boot-testcontainers, junit-jupiter, testcontainers - для тестирования.

- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) реализованы в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно. Спецификация Open API. Взаимодействие по RestFull API
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развёртывание: Требует остановки всего приложения.

### **4. Проблемы монолитного решения**

Текущее решение as-is не удовлетворяет новым требованиям развития бизнеса to-be

- Дефицит необходимой функциональности:
    - Управление пользователями, авторизация, аутентификация и администрирование
    - Управление, в частности подключение, сценарии использования и мониторинг состояния, разными типами обородования непостредственно самими пользователями
    - Биллинг услуг и управление платежами - т.к. это коммерческий продукт
    - Мобильное приложение, т.к. это уже must have для подобных приложений
- При реализации нового функционала в рамках текущего монолитного решения кратно повысится сложность системы, что приведет к росту количества ошибок и потребует больших ресурсов на решение проблем
- Ограничения масштабируемости. В варианте as-is система может масштабироваться вертикально, добавлением физических ресурсов. Но возможности горизонтального масштабирования ограничены и не получится масштабировать отдельные высоконагруженные сервисы в следствие роста количества клиентов и трафика, как пример, сервис видеонаблюдения.
- Проблемы с производительностью и доступностью. С ростом функционала, ростом количества клиентов и ростом трафика, Система как монолит с синхронным взаимодействием начнет работать медленнее, время бесперебойной работы - снизиться
- Проблемы с отказоустойчивостью. В случае сбоя в одном из компонентов системы, Система может перестать работать в целом 
- Развертываение системы требует выключения Системы - показатели доступности будут снижаться
